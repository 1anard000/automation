Part 2: Product Vision (15-20 min)

"What do you think Dify's product vision should be?"

"Dify's vision should be: the operating system for AI-native work. Not just a workflow builder — the platform where every team builds, deploys, and manages their AI agents.

Today, Dify is a tool — you build a workflow, deploy it, monitor it. Tomorrow, it should be a platform — like how GitHub went from 'a place to host code' to 'the operating system for software development.' GitHub added Actions (CI/CD), Packages (artifacts), Copilot (AI), Security (scanning) — each layer increased switching costs and ARPU. Dify should follow the same pattern.

The three layers of the vision:

Layer 1 (today): Build. Visual workflow builder, agent creation, RAG pipelines. This is the core product and it's already strong.

Layer 2 (next 12 months): Collaborate. The Human Input Node (v1.13.0) is the start — workflows that pause for human review. But collaboration goes deeper: team workspaces, role-based access, approval chains, audit trails. This is what enterprises need to adopt at scale. At Salesforce, I saw that enterprise adoption isn't about the best product — it's about the product that fits into existing governance structures.

Layer 3 (18-36 months): Ecosystem. The Creator Center and Template Marketplace are the right move — but they need to become a real ecosystem. Think GitHub Marketplace: third-party integrations, pre-built workflows, revenue sharing with creators. The platform that attracts the most creators wins. At GitHub, the Actions marketplace created massive switching costs — once you've built your CI/CD pipeline in GitHub Actions, migrating is painful. Dify needs the same dynamic."

"How do you think about balancing developer experience vs enterprise needs?"

"This is the core tension for any open-core company. I watched GitHub navigate it for years.

The answer is: the developer experience drives adoption, the enterprise features drive revenue. You don't sacrifice one for the other — you layer them.

At GitHub: the free tier was generous and developer-friendly. Developers loved it. Then enterprises needed SSO, audit logs, compliance — those were gated behind Enterprise. The developer experience got people in the door. Enterprise features got companies to pay.

For Dify, the same pattern applies:

Developer experience (free/open-source): Visual workflow builder, model-agnostic, self-hosted. This drives adoption. Don't restrict it.

Enterprise features (paid): SSO/SAML, multi-workspace, audit logs, RBAC, VPC deployment, SLAs. This drives revenue. Gate it.

The mistake to avoid: Don't restrict the core product so much that developers can't build anything useful for free. GitHub's generous free tier drove 180 million users. Dify's 200 messages/month sandbox might be too restrictive — I'd test whether a more generous free tier increases conversion."

Your background link: At GitHub, you watched this exact tension play out. The developer experience was never sacrificed for enterprise — it was layered. That's the playbook.

"What features would you prioritize in the next 12 months?"

"Three priorities, in order:

1. Team collaboration (highest priority). Right now, Dify is primarily a single-player builder. Enterprise adoption requires multiplayer: shared workspaces, role-based access, approval workflows, team-level analytics. At Salesforce, the product that won wasn't the best CRM — it was the one that fit into how sales teams actually work together. Dify needs to be the tool teams use together, not individually.

2. Evaluation and observability. Enterprises can't deploy AI workflows in production without knowing they work. Dify needs robust evaluation — can this workflow handle edge cases? What's the accuracy rate? Where does it fail? At GitHub, we built similar tooling for code quality — enterprises needed to trust that the code was good before deploying. Same dynamic here.

3. Marketplace ecosystem. The Creator Center launched in May 2026. The next step is making it a real ecosystem: revenue sharing with creators, certified integrations, template quality standards. At GitHub, the Actions marketplace created a flywheel — more templates → more users → more creators → more templates. Dify needs the same flywheel."

"How do you think about model-agnosticism as a product strategy?"

"This is Dify's biggest strategic advantage, and it's getting more valuable over time.

At GitHub, we saw the same dynamic with cloud providers. GitHub didn't lock you into AWS or Azure — it worked with any cloud. That neutrality was a feature, not a limitation. Enterprises don't want to be locked into one model provider — they want to use GPT for one task, Claude for another, Llama for a third, and DeepSeek for a fourth, depending on cost, performance, and compliance.

As models commoditize — and they are — the orchestration layer becomes more valuable. If you're locked into Microsoft Copilot Studio, you're stuck with Azure OpenAI. If you're locked into Google Vertex, you're stuck with Gemini. Dify lets you pick the best model for each task and switch when better models emerge.

The cost angle is huge. At GitHub, I saw that token costs were a real concern — Copilot was losing money on every user. Enterprises are going to face the same problem with AI workflows. Dify's model-agnostic approach lets them optimize for cost — use a cheap model for simple tasks, an expensive model for complex ones. That's a real selling point."

Your background link: At GitHub, you saw token economics firsthand. Copilot's cost problem is Dify's opportunity — model-agnostic means cost-optimized.

Part 3: Market Expansion (15-20 min)

"How would you think about expanding Dify's market?"

"I'd think about it in four dimensions: geographic, horizontal, vertical, and channel. Let me go deep on each.

Geographic expansion:

Dify is strong in China and APAC. The natural next step is Western enterprise — US and Europe. But the approach matters.

At Amazon AGS, I learned that going international isn't just about translating your product — it's about rebuilding trust in a new market. Chinese companies expanding to the West face a trust gap: Western enterprises worry about data sovereignty, security, and compliance. Dify already has SOC 2, ISO 27001, and GDPR — that's the foundation. But the next step is Western reference customers. You need 3-5 Western enterprise logos that you can point to and say 'they trust us.'

The entry strategy for the US should be: (1) land 3-5 design partners in the US — offer Enterprise tier at a discount in exchange for case studies and references. (2) Build a local GTM presence — even one person in the US who can do in-person meetings. (3) Attend enterprise AI conferences — Gartner, Forrester, AI-specific events. Western enterprises buy from companies they've met in person.

For APAC expansion beyond China: Japan is the most mature enterprise AI market in Asia. Dify already has a Tokyo office — that's the right beachhead. Then Korea, then Southeast Asia.

Horizontal expansion:

Dify started with developers. The blog content now targets IT leaders and marketers — that's the right expansion. But the execution matters.

At Salesforce, I learned that horizontal expansion works when you change the buyer, not just the user. The developer builds the workflow, but the IT leader approves the purchase. The marketer uses the output, but the CMO signs the contract. Dify needs to build different value propositions for different buyers:

  • For developers: 'Build AI workflows faster with a visual builder'
  • For IT leaders: 'Deploy AI workflows with enterprise governance and compliance'
  • For business users: 'Use AI workflows without writing code — the Human Input Node lets you participate in AI processes'

Each buyer needs different content, different pricing, different sales motions.

Vertical expansion:

Dify has proven logos in logistics (Maersk), pharma (Novartis), automotive (Volvo), education (ETS), and professional services (Deloitte). The next move is to double down on 2-3 verticals with dedicated solutions.

At Amazon, I saw that vertical solutions work when you understand the specific workflow. For logistics: document processing, customs compliance, shipment tracking automation. For pharma: clinical trial data processing, regulatory submission workflows, drug interaction analysis. For professional services: client onboarding automation, knowledge management, proposal generation.

Dify should build vertical-specific templates and case studies. A logistics company doesn't want a generic AI platform — they want a platform that already understands their workflows.

Channel expansion:

The partner program (Reseller, Service Partner, Marketplace Partner) is the right channel strategy. At Salesforce, the partner ecosystem was the primary growth engine — system integrators like Accenture, Deloitte, and PwC drove more enterprise adoption than the direct sales team.

In APAC, system integrators are the fastest path to enterprise adoption. These firms are already advising enterprises on AI strategy — if Dify is their recommended platform, that's instant pipeline.

In the US, the motion is different — it's developer advocacy and PLG. Developers adopt Dify for personal projects, bring it to work, enterprise follows. That's the GitHub playbook."

Your background links: Amazon AGS (geographic expansion trust gap) → Salesforce (horizontal expansion = changing the buyer, vertical solutions, partner ecosystem) → GitHub (developer advocacy PLG).

"How do you think about China vs international as a market priority?"

"Both are important, but the GTM motions are completely different.

China: Dify is already strong here. The opportunity is deeper penetration — more enterprise customers, more vertical solutions. In China, the sales motion is relationship-driven. System integrators and consulting firms are the channel. The local team in Shanghai/Suzhou handles this.

International: This is where the growth ceiling is. The international market is 10x the China market for enterprise AI platforms. But it requires a different approach — trust-building, compliance, local presence.

My recommendation: don't split focus equally. Instead, designate one person (potentially me) to own international GTM as a focused effort. In China, the existing team and partners continue the motion. International gets a dedicated owner who builds the playbook: design partners, case studies, local presence, conference strategy.

At Amazon AGS, the most successful international expansion happened when there was a dedicated owner for each market — not a team that split time between China and international. Focus beats breadth."

"How do you think about pricing for different markets?"

"This is where the GitHub model is instructive. GitHub's pricing was global — same price everywhere. But the value perception is different in different markets.

For Dify, I'd think about it in three tiers:

Self-serve (global): The Sandbox, Professional, and Team tiers should be the same price globally. $590/yr is accessible for a team in any market. Don't discount self-serve — it devalues the product.

Enterprise (regional): Enterprise pricing should be regional. US/European enterprises expect to pay more ($50-200K/yr for enterprise AI platforms). APAC enterprises have different price sensitivity. At Salesforce, we had regional pricing that reflected local market conditions.

Partner pricing: For resellers and service partners, offer wholesale pricing (30-40% discount) that lets them mark up and make margin. This incentivizes partners to sell Dify. At Salesforce, the partner margin structure was a key driver of partner-sourced revenue.

The key insight from GitHub: don't restrict the free tier based on geography. GitHub's free tier was the same everywhere — that's what drove global adoption. Dify should do the same. The free tier is the top of the funnel everywhere."

Your background link: At Salesforce, you saw regional pricing and partner margin structures. At GitHub, you saw global free-tier pricing driving adoption. Both apply to Dify.

The objections are: security, compliance, governance, support. Dify's enterprise tier addresses all of these. Part 7: CFO-Specific Questions (5-10 min)

"How do you think about unit economics for Dify?"

"This is where the orchestration layer thesis is strong. At GitHub, I saw that the model layer has unsustainable unit economics — Copilot was losing money on every user because of token costs. The orchestration layer is different.

Dify's cost structure is: infrastructure (hosting, compute) + support + sales. The model costs are passed through to the customer (they pay for their own API keys or self-host). That means Dify's gross margins can be much higher than model-layer companies.

The key unit economics metrics:

  • Gross margin: Should target 70-80% (infrastructure + support costs)
  • CAC payback: For self-serve, should be <6 months. For enterprise, <12 months.
  • LTV/CAC: Target 3:1 or better
  • Net Revenue Retention: Target 120%+ (seat expansion + tier upgrades)

The GitHub model is the benchmark: GitHub reached $2B+ ARR with strong unit economics because the product was sticky (switching costs from repos, Actions, integrations) and the expansion was natural (more seats, more features). Dify should aim for the same dynamics."

"How do you think about the open-source monetization challenge?"

"The classic open-source challenge is: how do you convert free users to paying customers? GitHub solved this with the 'enterprise compliance gate' — SSO, SAML, audit logs, self-hosted deployment. These features are free to implement but critical for enterprises. They're the paywall.

Dify has the same structure: Community Edition is free and powerful, but enterprises need SSO, multi-workspace, audit logs, VPC deployment, SLAs. Those are the gates.

The risk is that the Community Edition is too powerful — enterprises can self-host and never pay. GitHub faced this too. The answer was: make the cloud version better (easier to manage, automatic updates, integrations) so that even enterprises that could self-host chose the cloud version for convenience.

Dify should do the same: make Dify Cloud so good that even enterprises with the capability to self-host choose the cloud version. The self-hosted option exists for regulated industries that truly need it — but the cloud version should be the default."

Your background link: At GitHub, you watched the open-core monetization challenge play out firsthand. The enterprise compliance gate is the playbook.
